# SwiftUI と AppKit の落とし穴

## 状態と描画

- `@Published` は、同じ値の代入でも通知する。ドラッグや毎フレームのような高頻度の経路では、変化したときだけ代入する
- 通知は、プロパティが更新される前 (willSet) に出る。ハンドラは配信された値を使い、モデルを読み直さない
- Combine は、`.dropFirst().removeDuplicates()` の順だと、初回の同値でも発火する。初回を除きたいときは `.removeDuplicates().dropFirst()` にする
- `Canvas` は、中身が空でも毎フレームのコストがかかることがある。ソースから読めないので、操作中の CPU は計測で確かめる
- 巨大な選択可能テキスト (`Text` に `.textSelection(.enabled)` を付けて全行を結合したもの) は、ホバーやスクロールのたびに全体の計算が走って重くなる。大量の行は、`NSTextView` を包んだものに置き換える
- 入れ子の条件で要素を薄く (opacity) すると、外側と内側が乗算される。ヒットテストの無効化は乗算されないので、外側 1 か所でよい。どの条件の組み合わせでも段数が 1 になるよう、真理値表で確かめる

## ウィンドウとビュー

- `WindowGroup` を書くときは `id:` を渡す。省くと、ウィンドウ位置の保存キーが内容の型名から作られ、型によってはビルドごとに別のキーになって、設定が増え続けることがある
- ビューの生成・アタッチ・可視化の順は、フレームワークが決める。リセットや初期化の発火点は、内部の状態の遷移でなく、ウィンドウが開く・見え始めるといった見える出来事に置く。机上で「どの順でも通る」と数えても、想定の外の順が起きる
- 可視性は、通知の記憶でなく、実際の状態を読んで決める。ウィンドウの可視性は occlusion でなく visible で見る
- 定期描画は、ウィンドウを閉じても止まらないことがある (閉じても view が外れない)。閉じた通知だけをゲートにしない
- `NSWindow.isReleasedWhenClosed` の既定は true。閉じた瞬間に余分な release が送られ、参照を持っていると解放済みのアクセスになる。生成直後に false にする
- `NSWindowController` は、生成時にウィンドウの delegate を自分で取る。その前に代入した delegate は、何の診断もなく置き換わる。コントローラの生成後に代入する
- SwiftUI の中に置いた AppKit のビューは、重なった領域のクリックを取る
- メニュー項目の action 名に、設定を開く意味の語を使うと、OS が標準の設定コマンドと見なして、アイコンを付けることがある。原因は表示名でなく action 名なので、action 名を変えて確かめる
- `LSUIElement` のアプリは、Dock に出ない。アイコンを隠す設定を持つなら、メニューに届く経路を複数用意し、片方だけ変えない
