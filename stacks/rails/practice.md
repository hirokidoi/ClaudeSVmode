# Rails の作法

## 環境の確定

- runner やコンソールが接続する環境 (`RAILS_ENV`) を、調査の最初に確かめる。空の結果を「データが無い」と断言する前に、どの環境の DB を見ているかを確かめる
- DB の日時を根拠にする前に、アプリと DB のタイムゾーン設定を確定する。見るのは `config.time_zone`、Active Record の既定のタイムゾーン、DB のセッションのタイムゾーン
- 実装の前に、実データかフィクスチャで型と境界値 (存在の有無・0・null・空) を確かめる。設計書の型の記述が実データと違うことがある

## スキーマと migration

- migration の流儀 (外部キーの書き方・日時の精度など) は、プロジェクトの規約を先に確かめる
- `schema.rb` (または `structure.sql`) は手で編集しない。migration から生成する
- migration が不審な DDL を出したら (外部キーが黙って落ちる、精度が化ける、索引が重複する)、原因を疑う前に bootsnap のキャッシュを消してコールドで再実行する
- 稼働中のアプリがある DB で列を DROP しない。アプリは起動時に列の一覧をキャッシュするため、再起動までの間 INSERT が失敗する。先に `ignored_columns` でコードから外してから落とすか、停止中に適用する
- JOIN の条件を書く前に、結合先のスキーマを確かめる。外部キー名が似ていても、主キーとは限らない

## 画面と URL

- ERB の `<%= %>` は HTML をエスケープする。属性ごと文字列で出さず、`class="<%= … %>"` の形にする。`raw` や `html_safe` で回避しない。タグ名の直後に `<%=` が来る形はレビューで拾う
- `url_for` やパスヘルパは、今のリクエストのクエリ文字列を引き継がない。残したいパラメータは明示的に渡す

## クエリ

- 関連を辿るループは `includes` / `preload` で N+1 を防ぐ
- 高頻度に呼ばれる経路では、ループの中のクエリと、無駄な読み書きを数える
- 「関連が無いレコード」のスコープは、作成からの経過時間のような間接条件より、関連の欠如を直接表す書き方 (`where.missing` など。使える Rails の版を確かめる) を選ぶ

## 層の責務

- プロジェクトの規約が層の責務 (controller にクエリを書かない等) を定めていれば、それを設計とレビューの観点にする。規約に無いことを、この観点で指摘しない

## 定数

- 調整される値だけを定数にする。比較の向きや分岐のような構造に関わる値は、定数にせず構造として書く
- 定数の値を変えて落ちるテストは、期待値を直す前に、なぜ値に依存する作りだったかを問う (テストの書き方は testing.md)

## アセットと静的解析

- 開発と本番で、アセットのコンパイル結果が違うことがある。アセットの読み込み方を変えたら、本番相当のコンパイルで確かめる (手順は verification.md)
- Brakeman の警告は、コードを歪めて回避しない。本物か誤検知かを判断し、誤検知なら理由を付けて ignore ファイルに登録する
