# スタックパック

技術スタックごとの補足知識の置き場。ロール定義 (`roles/`) を補うもので、wf の共通引数 `stacks` で指定したときだけ読まれる。指定しなければ、ロール定義だけで進む。

## 担当の読み方

1. ロール定義を読む
2. 指定されたスタックごとに、そのパックの `index.md` を読む
3. `index.md` の表で、自分のロールに当たる行のファイルを読む。条件が付いた行は、条件の目印を対象のプロジェクトで確かめ、当てはまるときだけ読む
4. `index.md` が無いスタックは読まずに続け、成果物に「スタックパック未配置: <名前>」と書く

パックの内容が、ロール定義や wf のプロンプトの指定と食い違うときは、ロール定義とプロンプトに従う。

## ディレクトリ

`stacks/<スタック名>/` を 1 パックとする。スタック名は `stacks` に渡す文字列と一致させる。

| ファイル | 役割 |
|---|---|
| `index.md` | 入口。全パックに必須 |
| `verification.md` | 検証コマンドの例。任意 (テスト担当と SV が読む) |
| そのほか | 話題別のファイル。サブディレクトリを作ってよい |

## index.md の書き方

```
# <スタック名> パック

## 当てはまるプロジェクト
## 読むファイル
## SV への案内 (任意)
```

- 当てはまるプロジェクト: SV がスタックを判断する材料。プロジェクトにあるファイルや設定を目印として挙げる
- 読むファイル: 次の形の表。読むファイルが無いパックは「なし」と書く

```
| ファイル | 読み手 | 条件 |
|---|---|---|
| practice.md | investigator, designer | 常に |
```

- 読み手: ロール定義のファイル名で書く。`investigator` / `designer` / `implementer` / `reviewer` / `verifier` のいずれか
- 条件: 「常に」か、プロジェクトで確かめられる目印 (例: 特定の import があるとき)
- SV への案内: 対話で確かめておく点や、検証コマンドを組み立てるときに見る節

読み手の対応は、網羅性チェックと独立審査と UI レビューが `reviewer`、UI デザインと提案が `designer`、テストが `verifier` になる。

## verification.md の書き方

「検証コマンド」の節を持ち、コマンドの例を種別 (`kind`) 付きで並べる。SV はここから wf の `test_commands` を組み立てる。

- `build`: 成果物ができるか
- `test`: 自動テスト
- `launch`: 起動確認。起動、状態の確認、起動したプロセスの停止までを 1 つのコマンドで完結させ、起動したものを残さない

人の目が要る確認 (画面の見た目・許可ダイアログ・音) は載せない。それは SV がユーザに頼む実機確認になる。

## 新しいスタックの足し方

1. `stacks/<スタック名>/` を作る
2. `index.md` を書く
3. 表に挙げたファイルを書く
4. 表のファイルがすべて実在し、表に無いファイルがディレクトリに無いことを確かめる
5. `~/.claude/stacks/` に置く。許可設定は `Read(~/.claude/stacks/**)` で足りる
6. 小さな案件で `stacks` を指定して wf を起動し、成果物に「スタックパック未配置」が出ないことを確かめる

## 書き方の方針

- 各項目は、何をするか・しないかが読めば分かる形にし、理由を短く添える
- 担当は、自分に当たるファイルを毎回全文読む。条件で分けられる内容は別ファイルにする
- 確かめていない挙動は書かない。広く確立した事実と、プロジェクトで確かめられることに限る
- ロール定義に書かれている進め方の一般論は重ねない。そのスタックで何を見るか、どう確かめるかだけを書く

## 更新時の注意

キットの更新で、同じ名前のパックは上書きされる。自分で足すパックや、キットのパックへの加筆は、別の名前のディレクトリに置く。
